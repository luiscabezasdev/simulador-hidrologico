# Phase 0 Research: HidroLab Interactivo Pro

**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md)

No quedan marcadores `[NEEDS CLARIFICATION]` en `spec.md`: las tres ambigüedades detectadas en `/speckit-clarify` (mecanismo de teclado para aislar segmentos, coexistencia del aislamiento con el rastreo continuo, y desambiguación tap/drag en táctil) ya están resueltas en `## Clarifications`. Este documento cubre únicamente las decisiones técnicas de nivel de plan necesarias para implementar las tres capacidades sin violar el stack restringido (Constitución, Principio II) ni el modelo lineal por tramos (Principio IV).

## R14: Mecanismo de tema claro/oscuro

- **Decision**: Un atributo `data-tema` en `<html>` (`"claro"` o `"oscuro"`) conmuta un segundo bloque de variables CSS (`:root[data-tema="oscuro"] { --color-fondo: ...; }`) que sobreescribe las mismas variables ya usadas por todo `styles.css` (Principio VI, DRY: ninguna regla de color se duplica, todas leen las variables existentes).
- **Rationale**: Reutiliza la arquitectura de variables CSS ya existente (`--color-fondo`, `--color-texto`, `--color-primario`, etc.) sin introducir una librería de theming ni duplicar selectores; un solo atributo controlado por JavaScript vanilla decide el bloque activo.
- **Alternatives considered**: Dos hojas de estilo (`styles-claro.css`/`styles-oscuro.css`) — descartado porque viola la estructura de tres archivos exigida por Principio VI y duplicaría todo el CSS no relacionado con color; clases `.tema-oscuro` en `body` — funcionalmente equivalente a `data-tema`, se prefiere el atributo por ser el idioma nativo de `:root[attr]` y no interferir con otras clases de layout.

## R15: Detección y reactividad a la preferencia de tema del sistema

- **Decision**: En la inicialización, si `localStorage` no tiene una preferencia explícita guardada, se usa `window.matchMedia('(prefers-color-scheme: dark)').matches` para fijar el tema inicial (FR-003); además se suscribe un listener `change` sobre ese `matchMedia` que solo actualiza el tema en vivo mientras el usuario **no** haya elegido explícitamente un tema en esa sesión/navegador.
- **Rationale**: `matchMedia` es una API nativa del navegador (sin dependencias, Principio II); reaccionar en vivo (mientras no haya elección explícita) es coherente con FR-003 sin contradecir FR-002, que solo exige recordar una elección *explícita*.
- **Alternatives considered**: Verificar `prefers-color-scheme` solo una vez en la carga — descartado porque un usuario sin preferencia explícita que cambia el modo oscuro de su sistema operativo mientras la pestaña sigue abierta esperaría ver el simulador reaccionar, y la API de eventos lo permite sin costo adicional.

## R16: Persistencia de la preferencia de tema

- **Decision**: `localStorage.setItem('hidrolab-tema', 'claro' | 'oscuro')` solo cuando el usuario acciona explícitamente el alternador (FR-002); lectura envuelta en `try/catch` — si `localStorage` no está disponible (modo privado, almacenamiento deshabilitado) la función de guardado/lectura falla en silencio y el sistema recae en la preferencia del sistema operativo en cada carga (edge case de `spec.md`), sin mostrar errores al usuario (Principio VII).
- **Rationale**: `localStorage` es una API del navegador, no un backend ni una base de datos externa; es exactamente el mecanismo que la Constitución permite para estado del lado cliente (ningún principio lo prohíbe, y el Principio II solo veta APIs de red y backends). Coincide con la Assumption "Persistencia de tema" de `spec.md`.
- **Alternatives considered**: Cookies — descartado por ser semánticamente para transmisión servidor-cliente (inexistente aquí) y por requerir gestión de expiración innecesaria; `sessionStorage` — descartado porque no sobrevive a cerrar y reabrir el navegador, lo que violaría FR-002/SC-004 ("en visitas futuras... incluso en una sesión posterior").

## R17: Paleta de contraste del tema oscuro (WCAG 2.1 AA)

- **Decision**: El tema oscuro define su propio conjunto de valores para las mismas variables (`--color-fondo`, `--color-superficie`, `--color-texto`, `--color-texto-secundario`, `--color-borde`, `--color-primario`, `--color-primario-claro`, `--color-exito`, `--color-error`), cada uno verificado manualmente (herramienta de contraste del navegador o WebAIM) para mantener ≥4.5:1 en texto y ≥3:1 en líneas/áreas del gráfico y del estado de verificación, replicando exactamente el criterio ya aplicado al tema claro (comentario en `styles.css` línea 19-26).
- **Rationale**: FR-004 exige el mismo estándar ya alcanzado por el tema claro; reutilizar el mismo conjunto de nombres de variable garantiza que ningún selector de `styles.css` necesite lógica condicional de tema — la cascada CSS resuelve el color correcto automáticamente.
- **Alternatives considered**: Invertir automáticamente los colores claros con un filtro CSS (`filter: invert()`) — descartado porque distorsiona el matiz de `--color-primario`/`--color-exito`/`--color-error` de forma impredecible y puede romper el contraste verificado en vez de garantizarlo.

## R18: Algoritmo de interpolación continua Q(t)

- **Decision**: Una función pura nueva `interpolarCaudal(segmentos, t)` recorre los `SegmentoModelo[]` ya producidos por `calcularSegmento()` (Principio IV) y ubica el segmento `i` tal que `tInicio ≤ t ≤ tFin`; el valor devuelto es `fᵢ(t) = QInicio + pendiente · (t - tInicio)` — la misma fórmula ya usada por `calcularIntegral()`, sin introducir una segunda definición (DRY, Principio VI). Si `t` está fuera de `[tInicio del primer segmento, tFin del último segmento]` del modo activo, retorna `null` (FR-012).
- **Rationale**: Reutilizar `SegmentoModelo` (ya validado y verificado por `verificarResultados()`) garantiza que el valor interpolado sea matemáticamente coherente con el volumen ya calculado (FR-010), sin recalcular pendientes ni tocar `DATOS_ORIGINALES`.
- **Alternatives considered**: Recalcular la pendiente ad-hoc en cada movimiento del cursor con búsqueda lineal sobre `DATOS_ORIGINALES` — descartado por duplicar la fórmula de `calcularSegmento()` (violaría DRY, Principio VI); dado que solo hay 5 segmentos, una búsqueda lineal sobre `segmentos` (no sobre datos crudos) es trivialmente eficiente y no requiere búsqueda binaria.

## R19: Mapeo de posición de puntero a instante t (hit-testing)

- **Decision**: Se extrae de `actualizarGrafica()` un cálculo de escalas compartido (`calcularEscalasGrafico(ancho, alto, resultado)`) que retorna los mismos parámetros de margen/escala (`escalarT`, `escalarQ`, límites) ya usados para dibujar; el manejador de movimiento de puntero invierte `escalarT` (`t = tMin + ((x - margen.izquierda) / anchoGrafico) * (tMax - tMin)`) para convertir la posición horizontal del evento en un instante t, que luego se pasa a `interpolarCaudal()`.
- **Rationale**: Evita duplicar la lógica de escalado (Principio VI, DRY) entre el dibujo y la interacción; garantiza que el punto mostrado al usuario esté siempre alineado píxel a píxel con la curva dibujada.
- **Alternatives considered**: Recalcular márgenes/escala de forma independiente en el manejador de eventos — descartado por riesgo de desincronización visual si un valor de margen cambia solo en un lugar.

## R20: Desambiguación de gestos táctiles (tap vs. press-and-drag)

- **Decision**: Se usa la Pointer Events API (`pointerdown`, `pointermove`, `pointerup`, `pointercancel`) sobre el canvas. En `pointerdown` se registra posición y tiempo de inicio. Si `evento.pointerType === 'mouse'`, todo `pointermove` (sin necesidad de botón presionado) activa el rastreo continuo, y un `click`/`pointerup` con desplazamiento mínimo activa la selección de segmento — replicando el comportamiento estándar de hover + click. Si `evento.pointerType === 'touch'`, el rastreo continuo solo se activa cuando el movimiento acumulado desde `pointerdown` supera un umbral pequeño (p. ej. 8px) antes de `pointerup` (interpretado como "mantener presionado y arrastrar"); si `pointerup` ocurre sin superar el umbral, se interpreta como un toque breve (tap) y se ejecuta la selección/deselección del segmento tocado (FR-009, edge case de `spec.md`).
- **Rationale**: Pointer Events unifica mouse/touch/pen en una sola API nativa (sin dependencias); el umbral de movimiento es la técnica estándar para distinguir tap de drag en superficies táctiles, consistente con el patrón "tap vs. press-and-drag" descrito explícitamente en la clarificación de `spec.md`.
- **Alternatives considered**: Escuchar `touchstart`/`touchmove`/`touchend` por separado de `mousemove`/`click` — descartado porque duplica la lógica de hit-testing y de umbral en dos rutas de código distintas (viola DRY); Pointer Events cubre ambos casos con un único conjunto de manejadores.

## R21: Aislamiento de segmento — estado y leyenda accesible

- **Decision**: Estado transitorio en memoria (`segmentoAisladoIndice: number | null`, sin persistencia — coherente con R7 de `research.md` de la feature 001) gestionado por dos funciones de interfaz: `aislarSegmento(indice)` (alterna: si `indice` ya está aislado, limpia; si no, lo fija) y `limpiarSeleccionSegmento()` (fija `null` incondicionalmente). Ambas se disparan desde: (a) clic/tap sobre el segmento en el canvas (hit-testing por rango de t, igual que R19), y (b) una leyenda de 5 botones (`<button aria-pressed="...">`) fuera del canvas, uno por segmento, más un botón "Mostrar periodo completo" que llama a `limpiarSeleccionSegmento()` (FR-005, FR-007, Clarifications sesión 2026-09-16).
- **Rationale**: `aria-pressed` en botones nativos es el patrón WCAG estándar para controles de alternancia (toggle) accesibles por teclado sin roles ARIA compuestos frágiles (evita `role="radiogroup"`, que no soporta deselección nativa). El botón explícito de limpiar cubre el camino alternativo mencionado en FR-007 y en la Assumption "Interacción de selección de segmento".
- **Alternatives considered**: `<select>` con 6 opciones (5 segmentos + "todos") — descartado porque no permite la interacción de "clic directo sobre el gráfico para aislar" de forma bidireccional obvia con una lista de select; grupo de radios (como el selector de intervalo ya existente) — descartado porque los radios nativos no soportan deseleccionar el que ya está marcado sin JavaScript adicional que replicaría el mismo comportamiento de los botones `aria-pressed`.

## R22: Extensión de la nomenclatura de módulos (Principio VI)

- **Decision**: Los ocho módulos exigidos textualmente por la Constitución (`validarDatos`, `calcularSegmento`, `calcularIntegral`, `calcularTrapecio`, `verificarResultados`, `calcularPeriodo`, `actualizarGrafica`, `actualizarInterfaz`) se conservan sin cambio de nombre ni de responsabilidad central; `actualizarGrafica()` y `actualizarInterfaz()` amplían su firma para recibir el nuevo estado de interacción (tema ya no les concierne — se aplica a nivel de `document.documentElement`, fuera del canvas/panel — pero sí reciben `segmentoAisladoIndice` y `puntoRastreo`, ver `data-model.md`). Las capacidades nuevas que no encajan en los ocho módulos originales (interpolación continua, gestión de tema, gestión de puntero, leyenda de segmentos) se implementan como funciones adicionales con nombres semánticos propios, documentadas en `contracts/interaccion-avanzada.contract.md`.
- **Rationale**: El Principio VI (a diferencia del Principio III) no está marcado NON-NEGOTIABLE y su intención declarada es "nombres semánticos" y "sin duplicar fórmulas", no una lista cerrada que prohíba cualquier función adicional; HidroLab Interactivo Pro introduce capacidades genuinamente nuevas (tema, aislamiento, rastreo) que no existían cuando se escribió esa lista para la feature 001. Renombrar o forzar estas capacidades dentro de los ocho nombres originales sería más confuso que darles nombres propios y claros.
- **Alternatives considered**: Meter toda la lógica nueva dentro de `actualizarInterfaz()` como un monolito — descartado porque violaría la claridad semántica que el propio Principio VI exige y dificultaría probar cada capacidad de forma aislada (Independent Test de cada User Story en `spec.md`).
